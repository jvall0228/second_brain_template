# 29. Triage archival, periodic traces, and the agent logs (`brain triage-archive`, `brain trace`, `brain gap`, `brain accepted`)

*Section 29 of the [`brain` spec](../SPEC.md); section numbers are stable and `§N.x` references across the spec point at these files.*

The first two commands are the mechanical half of [triage-inbox](../../../skills/triage-inbox/SKILL.md) step 10. They exist because the same two operations done as free-form prose instructions produced broken links (a `../05_Areas/x.md` copied from `02_Inbox/` into `07_Archives/inbox/` points nowhere), broken structure (a second H1 inside a monthly log), duplicated runs after an interrupted application, and lost traces when two captures filed to one destination on one day. All four commands are zero-write previews by default and write only with `--write`; each ends a write by running §10 validation over the resulting corpus and exits 1 when it reports errors, so a transformation defect is caught before the commit. None needs an environment selection. Writes are atomic same-directory replacements through an authenticated parent (no symlinked component is ever followed); deletes refuse anything but a regular file.

**Write model (lost-update protection).** Every command computes a plan from the bytes it read and then replaces files; two invocations racing on one target would otherwise keep only the second. Two mechanisms close that: (1) the CLI takes the **vault write lock** — an exclusive `flock` (Windows: `msvcrt.locking`) on `.second-brain/write.lock`, ignored by git and opened without following symlinks — *before* computing the plan and releases it after the write, so concurrent invocations serialize and the later one plans from the earlier one's result; (2) every apply is a **compare-and-swap**: the plan records the bytes each target held when it was computed (`None` for a file that must not exist yet) and the write refuses with `WriteConflictError`, mutating nothing, if the target differs at write time; deletes use the authenticated claim protocol below. The comparison and replacement run under the same lock — it is re-entrant within a process, so the writer takes it whether or not the caller already holds it — which closes the window between them. A caller that computes plans through the Python API without the lock therefore cannot overwrite a sibling's write either: the stale plan fails and is recomputed. The lock blocks on POSIX (`flock`) and polls with a bounded wait on Windows; a `.second-brain` path that is a symlink or a stray file is refused as a command error.

**Authenticated source removal and recovery.** Triage and Inbox ingestion read source bytes through the complete no-follow vault-relative reader. Final opens are nonblocking where supported, so unexpected FIFOs are rejected as non-regular files without waiting for a writer. Their Python plans retain the source inode identity, parent-chain identities, and digest internally; those fields are not emitted in CLI JSON. A write checks that snapshot and safe-removal platform support before publishing destination changes. The entire apply, including API callers, holds the vault write lock.

Deletion is a claim-and-verify operation, not a pathname check followed by unlink. Before claiming, it fsyncs a per-source, vault-root `.brain-note-removal-<path-hash>.json` record and the vault directory. Keeping the record outside the source parent makes a replaced or moved Inbox detectable on retry. The record binds the original relative path, expected file/parent identities, digest, and unique `.brain-note-removal-<random>.source` quarantine. No-replace rename through a held, authenticated parent claims the source; identity and digest are checked on the claimed object before deletion. A changed source is restored without overwrite when possible. A recreated original pathname is never deleted. Restore collisions, changed parents, malformed records, or changed claimed files preserve evidence and report `recovery required`.

Before interpreting a missing source as complete, both preview and write consult the removal record. A valid retained claim supplies the original bytes for normal archive-marker or gap-row deduplication; a write resumes removal without duplicating destination content. A prepared record whose original has not yet been claimed also resumes normally. If both original and claim are absent while the record remains (for example, termination after deletion but before record cleanup), the command reports recovery required rather than guessing completion. Recovery after displaced parent directories or foreign evidence likewise requires owner inspection. Successful operations remove their records and claims; interrupted evidence is hidden from the corpus and ignored by Git through `.brain-note-removal-*`. Do not delete recovery evidence until its destination and ownership have been checked.

Safe source deletion currently requires POSIX descriptor-relative operations plus macOS `renameatx_np` or Linux `renameat2` no-replace semantics. Other platforms retain read-only preview but refuse archive/ingest writes before destination publication; there is no unsafe check/unlink fallback.

**Privacy provenance.** Writers classify authenticated snapshots, including the exact captured bytes they transform, using effective privacy rather than only explicit tags. Summarized public traces and accepted-proposal copies record their source paths in `privacy-sources`; gap rows record nearest-note dependencies. Archival and gap ingestion preserve underlying dependencies when removing the source note. Existing provenance is merged and malformed provenance is refused. Private/unknown traces retain only a bare link; archive copies inherit `restricted/private`; public log ingestion refuses private/unknown substance unless gap ingestion explicitly declassifies it. Later source reclassification therefore prevents public-only reuse of a retained derivative.

## 29.1 `brain triage-archive <report> [--write]`

`<report>` is a note directly under `02_Inbox/` named `YYYY-MM-DD-<slug>.md`; the date names the month log `07_Archives/inbox/YYYY-MM-triage-log.md`. The transformation of the report body is deterministic: frontmatter is stripped; the first level-1 heading (the document title) is dropped; every other ATX heading (§7 grammar, outside fenced code) is demoted one level so the report nests under the run heading; every relative inline link destination outside fenced code and code spans is rebased from `02_Inbox/` to `07_Archives/inbox/` with the §5 parser (fragments, titles, `<angle>` destinations, escaped labels preserved; external, root-relative, placeholder, and vault-escaping destinations left alone); leading and trailing blank lines are trimmed. The appended section is

```
## YYYY-MM-DD — <report title>

<!-- triage-archive: <report path> sha256:<digest of the report bytes> -->
*Run: <author>, <session>*

<transformed body>
```

with title, author, and session taken from the report's frontmatter (`—` when absent) and rendered as one prose line each (link, comment, and code syntax escaped). A missing month log is created with `type/log`, `status/done`, `audience/agent`, `audience/human`, the H1 `# Triage Log — YYYY-MM`, and a one-paragraph notice; an existing one gets its `updated:` bumped to the vault's today.

**Identity and retries.** The HTML comment is the run's identity, and the **whole value** counts — source path *and* digest of the source bytes. Actions: `create` (no log yet), `append`, `delete-only` (the exact identity is already present — an earlier run wrote the log and was interrupted before the delete), `done` (source gone and the path already archived, or the restricted note already moved), `missing` (source gone, nothing archived — an error), and `conflict` (the same path is archived with a **different** digest: the report changed after it was archived, or a same-named report was recreated). A conflict mutates nothing and exits 1 in preview and write alike; `--revise` turns it into an `append` of a distinct section headed `… (revision N)` with its own marker, so a changed report is archived as a new version rather than deleted unarchived. Write order is log first, source delete second (the delete re-verifies the source digest), so a recoverable interruption leaves a state the next run finishes without a second copy (unrecognized removal evidence requires owner inspection as specified above); two runs of an archived report are byte-idempotent.

**Restricted reports.** A report classified private or unknown from its captured bytes and effective source dependencies never enters the month log (which stays non-restricted): it is moved to `07_Archives/inbox/<same name>` with an inherited `restricted/private` tag, `workflow/draft`/`workflow/review` removed, `status/done` added, links rebased the same way, the same identity marker inserted after its H1, and `updated:` bumped. An existing archived note of that name is compared by marker: the same digest is a finished or interrupted move (`delete-only`/`done`); a different digest or no marker is a `conflict` that leaves both files alone — the archived note is never overwritten.

JSON: `{action, archived?, archivedPresent?, conflict?, date, identity, identityPresent?, log, logPresent?, priorVersions?, report, restricted, section?, sourcePresent, steps, validation?}`; the preview's human output prints the section that would be appended.

## 29.2 `brain trace --date D --destination P --summary S --id I [--kind project|area] [--write]`

Traces one filed capture into the periodic notes for its **event date** `D`, never the triage date. Targets: `03_Journal/periodic/daily/D.md` and `03_Journal/periodic/weekly/<week>-review.md`, where `<week>` is the ISO week-year and ISO week of `D` (`date.isocalendar()`), so 2027-01-01 traces into `2026-W53-review.md` and 2024-12-30 into `2025-W01-review.md`. The entry is one line, `- [<label>](<source-relative path to P>) <!-- trace: I -->`, appended under `### Activity Log` in the daily note, under `## Get Clear` in the weekly note, and — with `--kind` — under `## Get Current — Projects` or `## Get Current — Areas` as well. The label is `S` collapsed to one line with link, HTML, and code syntax escaped; when `P` has private or unknown effective privacy the label is its title (or path when unavailable) instead and the summary is dropped (§10.2: a bare link propagates nothing, a summary would). The identity `I` (by convention the capture's original Inbox path) is collapsed to one line and may not contain `-->`.

**Missing notes are instantiated** from `09_Templates/template-daily-log.md` / `template-weekly-review.md`: relative links written from `09_Templates/` are rebased to the target directory first, then `{{date}}`, `{{WEEK_ID}}`, and the related-note tokens are filled (`{{PREVIOUS_DAILY_NOTE}}` and `{{RELATED_MONTHLY_REVIEW}}` only when that note exists — otherwise the line is dropped, never a dangling link), the goal placeholder lines (`{{CONTEXT}}`/`{{GOAL}}`, and the work variant's `{{HIGH_PRIORITY_GOAL}}`, `{{MEDIUM_PRIORITY_GOAL}}`, `{{LOW_PRIORITY_GOAL}}`) are dropped for a backfilled day, and any placeholder still present is an error, so an instantiated note always validates. An existing note is appended in place (after the section's last non-blank line; the template's empty `-` bullet is replaced) and its `updated:` bumped; a note that lacks the target section is an error and nothing is written.

**Identity dedupe.** A note that already carries `<!-- trace: I -->` is skipped, whatever the destination — so two distinct captures filed to one destination on one day both land, and re-running one capture (even with different summary text) is byte-idempotent. Section insertion is deterministic, so the rendered bytes are a function of the note, the arguments, and the vault's today.

JSON: `{date, destination, identity, label, notes: [{action: create|append|skip, path, sections}], steps, substanceDropped, validation?, weekId}`.

## 29.3 `brain gap --question Q [--term T]… [--nearest P]… [--sensitive] [--inbox] [--write]`

The only writer of the [vault-answer](../../../skills/vault-answer/SKILL.md) gap queue `10_Agents/docs/vault-answer-gaps.md`. The row is `- [ ] <today> — <question> — searched: `t`, `t` — nearest: [label](path), … <!-- gap: <id> -->` — the trailing marker is the row's **identity**, the first 16 hex digits of SHA-256 over `<today>|<question as logged>` — with the question and every term collapsed to one line, the question's link, HTML, comment, and code syntax escaped (`[`, `]`, `<`, `>`, `` ` ``, `\`) and truncated at 300 characters, and backticks inside a term replaced — so no question can open a heading, list item, fence, link, or comment in the queue. A nearest note that exists is linked by its title; a nearest note carrying `restricted/private` is linked by its **path** only, never its title or any substance. The row is inserted after the last non-blank line of `## Open and filled gaps`, and `updated:` is bumped; a queue that already carries the identity is a `skip` (the same question logged twice on one day is one row).

**Sensitivity routing.** A gap is sensitive when `--sensitive` is passed (the question itself is private) or when any nearest note is private or unknown. A sensitive gap never touches the public queue: the row is written to a new `02_Inbox/<today>-vault-answer-gap[-N].md` capture tagged `restricted/private` (plus `type/note`, `audience/agent`, `workflow/draft`, `author: brain`), and triage decides where the row lives. `--inbox` (the autonomous execution class, Inbox-first rule) writes the same capture without the restricted tag for a non-sensitive gap. Preview by default; `--write` writes one file atomically and validates the corpus. JSON: `{action: append|capture|skip, path, restricted, row, sensitive, steps, validation?}`.

**Ingestion (`brain gap --ingest <capture> [--declassify] [--write]`).** The consumer of the captures above, run at triage: the capture must sit directly under `02_Inbox/` with `author: brain` and a title starting `Vault answer gap`; every gap row in it (a `- [ ]`/`- [x]` line outside fenced code, carrying exactly one `gap` marker) is rebased from `02_Inbox/` to `10_Agents/docs/` and inserted into the queue unless its identity is already there; then the capture is deleted (compare-and-swap on the queue, digest check on the capture, under the vault write lock — §29 write model). A capture with private or unknown effective privacy is refused unless the owner passes `--declassify`, which is the explicit triage decision that a private question may enter the public queue; the JSON records `declassified: true`. Idempotent: re-ingesting an equivalent capture reports every row as `skipped` and changes no bytes. JSON: `{action: ingest, capture, captureDigest, declassified, ingested, path, restricted, rows, skipped, steps, validation?}`.

## 29.4 `brain accepted --ingest <report> [--write]`

The consumer of an autonomous [self-improve](../../../skills/self-improve/SKILL.md) run's accepted-proposal rows. The report must sit directly under `02_Inbox/`, must have public effective privacy, and must hold a `## Accepted proposals` section (§7 heading grammar, ending at the next level-1 or level-2 heading) whose first table row is exactly the log's header, `| Date | Proposal | What changed | Verification owed |`. Every following table row (separator rows skipped, four cells required) is rebased from `02_Inbox/` to `10_Agents/docs/` and appended after the last row of the log's table in `10_Agents/docs/accepted-proposals.md` unless a row with the same whitespace-normalized text is already there; `updated:` is bumped when anything was added. The report itself is left in place — it is still the retrospective that triage files. Idempotent by exact-row identity; write through the §29 write model. JSON: `{action: ingest, ingested, path, report, skipped, steps, validation?}`.
