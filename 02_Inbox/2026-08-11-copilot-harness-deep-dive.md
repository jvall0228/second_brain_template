# Copilot Harness Deep Dive

Focused re-verification (2026-08-11, later the same day as [[02_Inbox/2026-08-11-harness-primitives-research|the M6 harness research]]) of GitHub Copilot's agent surface, produced to ground the promotion of the Copilot adapter from P1 to first-class support. Five parallel research agents read the live GitHub and VS Code documentation pages directly (not summarization passes); load-bearing claims quote their sources. **This note supersedes the Copilot section of the M6 research note** — that section's five recorded gaps are resolved below, and several of its claims are corrected. Facts are accurate as of the date above; re-verify before relying on paths.

## Headline corrections to the M6 baseline

1. **Hooks are not VS Code-only — the Copilot CLI and the cloud agent both execute repo hooks.** GitHub's hooks concept page: "Hooks are available for use with: Copilot cloud agent on GitHub. GitHub Copilot CLI in your terminal." Config is `.github/hooks/*.json` (repo; the cloud agent only reads it **from the default branch**) plus `~/.copilot/hooks/*.json` (CLI user scope). The M6 baseline marked all of this unverified. ([hooks concept](https://docs.github.com/en/copilot/concepts/agents/hooks), [hooks reference](https://docs.github.com/en/copilot/reference/hooks-configuration))
2. **Git pre-commit hooks likely do not fire on cloud-agent commits.** No doc addresses local git commit mechanics; the cloud agent's commits are "authored by Copilot" and "signed, so they appear as Verified" — which suggests they are not produced by an ordinary local `git commit` (inference, not a doc statement). The sanctioned in-session interception mechanism is agent hooks (`preToolUse` can deny tools; `agentStop` can block completion). The vault's `.githooks/pre-commit` enforcement therefore has a **cloud-agent gap** that an agent hook must close. ([responsible use](https://docs.github.com/en/copilot/responsible-use/copilot-cloud-agent))
3. **Symlinked skills are unreliable in the Copilot CLI.** Issue [copilot-cli#1021](https://github.com/github/copilot-cli/issues/1021) (closed, no visible fix): `/skills list` "only detects skills in real directories" and "ignores skills that are accessed via symlinks". Related reports (#2161, #2230, seen as snippets) say `~/.agents/skills/` itself is not reliably discovered by the CLI. **The onboard-harness claim that the `~/.agents/skills/` symlinks cover Copilot is not safe.** The robust mechanism is registering the vault's *real* skills directory: `copilot skill add <dir>` / in-session `/skills add` (CLI), `chat.agentSkillsLocations` (VS Code).
4. **`.github/copilot-instructions.md` is the only repo instruction channel for several surfaces.** Per the [support matrix](https://docs.github.com/en/copilot/reference/custom-instructions-support): github.com Copilot **Chat** reads personal + repo-wide + organization instructions only — **no `AGENTS.md`**; Eclipse Chat reads repo-wide only; Visual Studio Chat reads repo-wide + path-specific. Instruction files **combine** — "all sets of relevant instructions are provided to Copilot"; no file suppresses another (the only winner-takes-all rule is nearest-`AGENTS.md`-wins among multiple `AGENTS.md`).
5. **The Copilot CLI has a real `@`-include mechanism** (baseline said "no import mechanism"): in `.github/copilot-instructions.md`, `AGENTS.md`, or `CLAUDE.md`, `@relative/path` includes another file, recursively. Not expanded in `GEMINI.md` or `*.instructions.md`; absolute paths and `~/` paths are **not** loaded. So the vault's one-line `CLAUDE.md` (`@AGENTS.md`) is genuinely expanded by the CLI — and the CLI "removes duplicate copies of identical" instruction files, so the shim costs nothing there. ([CLI custom instructions](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-custom-instructions))
6. **Terminology: the async agent is now branded "Copilot cloud agent"** (matching the `excludeAgent: "cloud-agent"` value); old "coding agent" URLs still resolve.

## Per-surface facts

### Instructions & entrypoints

- Three repo instruction types: repo-wide (`.github/copilot-instructions.md`), path-specific (`.github/instructions/**/NAME.instructions.md`, subdirectories searched; frontmatter `applyTo` glob — `**` = always, comma-separated multi-patterns — plus optional `excludeAgent: "code-review"|"cloud-agent"`), and agent files (`AGENTS.md` anywhere in the tree, nearest wins; root `CLAUDE.md`/`GEMINI.md` as alternatives, no documented tiebreak among agent files).
- Support matrix highlights: cloud agent and Copilot CLI read all three types (CLI also reads `.claude/CLAUDE.md`, user-level `~/.copilot/copilot-instructions.md` + `~/.copilot/instructions/**/*.instructions.md`, and `COPILOT_CUSTOM_INSTRUCTIONS_DIRS`). **Code review reads repo-wide + path-specific + `AGENTS.md` only** (not CLAUDE/GEMINI). VS Code Chat reads repo-wide + path-specific + `AGENTS.md` (`chat.useAgentsMdFile`; nested via experimental `chat.useNestedAgentsMdFiles`; `chat.useClaudeMdFile` for CLAUDE.md). JetBrains docs self-contradict (reference matrix says path-specific supported; the IDE how-to says repo-wide only).
- Priority personal → repository → organization, but **combined, never replaced**.

### Skills

- Agent Skills (agentskills.io) are first-class: cloud agent, code review, Copilot CLI, the Copilot app, agent mode in VS Code and JetBrains. Project paths: `.github/skills/`, `.claude/skills/`, `.agents/skills/`; personal paths per GitHub docs: `~/.copilot/skills` or `~/.agents/skills` (only VS Code's docs add `~/.claude/skills`). Extra project locations: `chat.agentSkillsLocations` (VS Code), `/skills add` / `copilot skill add <FILE|URL|DIRECTORY>` (CLI).
- Frontmatter: `name` (≤64 chars, lowercase/digits/hyphens, must match folder; invalid names **silently fail to load** in VS Code) + `description` (≤1024); optional `license`, `compatibility`, `metadata` (string map — the spec's sanctioned home for extra data), `allowed-tools` (experimental; CLI documents only `allowed-tools: shell`/`bash` with a trust warning). Extra top-level keys (the vault's `title`/`tags`/`updated`): tolerance undocumented, but `gh skill install` itself writes provenance keys into frontmatter and skills still work — tolerated in practice.
- `gh skill` exists (public preview, gh ≥ 2.90.0): search/preview/install (`@TAG`/`@SHA`, `--pin`, `--agent`, `--scope`)/update/publish (validates against the spec).
- No documented cross-path precedence for duplicate names; CLI built-ins can "intermittently override" same-named user skills ([#2146](https://github.com/github/copilot-cli/issues/2146)). **Avoid the nine CLI built-in names**: analyze, design, document, fix, investigate, research, security, test, verify. (None of the vault's twelve skills collide.)

### Copilot CLI

- Config `~/.copilot/config.json` (relocatable via `COPILOT_HOME`), trust stored in its `trustedFolders` array; trust gates where the CLI can "read, modify, and execute files" (session-only or persistent grants; content-loading gates undocumented).
- Permissions: `--allow-tool`/`--deny-tool`, comma-separated filters. Semantics: `shell(npm test)` = **exact** command; `shell(git:*)` = all subcommands (colon-wildcard is the only shell wildcard); `write(name)` = ends-with path match; `url(...)` filters; MCP as `Server(tool)`. **Deny always beats allow, even under `--allow-all`/`--yolo`.** Saved tool approvals: `~/.copilot/permissions-config.json`, location-scoped; URL approvals: `~/.copilot/settings.json`, global. For the vault: `--allow-tool='shell(python3 10_Agents/tools/brain/brain.py)'` covers the exact bare invocation only (argument-matching undocumented); `shell(python3:*)` covers all python3 use; a `preToolUse` hook is the precise option.
- Programmatic: `copilot -p PROMPT` (plus `-s`, `--share=PATH`, `--share-gist`, `COPILOT_MODEL`, token via `COPILOT_GITHUB_TOKEN`/`GH_TOKEN`/`GITHUB_TOKEN`).
- MCP: `~/.copilot/mcp-config.json`, `/mcp add`.
- Hooks: full support, loaded policy (`/etc/github-copilot/policy.d/`) → user (`~/.copilot/hooks/`) → repo (`.github/hooks/*.json`) → plugin; also inline in `.github/copilot/settings.json`[`.local`] and `~/.copilot/settings.json`.

### Cloud agent

- Ephemeral Actions-powered environment, destroyed per session; single-repo write scope; **59-minute cap per session** (a PR can span multiple sessions — `@copilot` follow-ups remember context); Ubuntu x64 / Windows runners only.
- Pushes to exactly one branch: a new `copilot/` branch (opening a draft PR immediately), or the existing PR branch when invoked via `@copilot`. Never the default branch.
- **CI gate:** Actions workflows on its PRs "require approval from a user with write access" by default ("Approve and run workflows"); a repo setting (Settings → Copilot → cloud agent → "Actions workflow approval") can disable the gate. The vault's validate CI is therefore **not automatic** on cloud-agent PRs unless the owner flips that setting.
- `copilot-setup-steps.yml`: single job that "MUST be called copilot-setup-steps", read from the **default branch**; only `steps`, `permissions`, `runs-on`, `services`, `snapshot`, `timeout-minutes` (≤59) may be customized. (The vault needs none — `brain` is stdlib-only.)
- Hooks: `.github/hooks/*.json` from the default branch, run inside the sandbox, `bash`/`command` fields only (`powershell` ignored); events = the GitHub set minus `permissionRequest`/`notification`; **`ask` decisions are downgraded to `deny`**.
- MCP: JSON in repo settings on github.com (shared with code review) — not committable. GitHub MCP + Playwright MCP on by default (read-only). Egress firewall on by default (Bash-tool processes only; not MCP or setup steps); repo-level override only when the org allows.
- Secrets: dedicated **Agents** secrets/variables (Settings → Secrets and variables → Agents), exposed as env vars; `COPILOT_MCP_`-prefixed ones go only to MCP servers; the agent cannot read Actions/Codespaces/Dependabot secrets.
- Entry points: agents panel, dashboard, Chat `/task`, issue assignment, "Fix with Copilot", `@copilot` PR mentions, integrations (Jira/Linear/Slack/Teams), REST API (`POST /agents/repos/{owner}/{repo}/tasks`, public preview, user-to-server tokens only), `gh agent-task` (gh ≥ 2.80.0), gh-aw scheduled workflows.

### Hooks (cross-surface schema)

- GitHub schema (CLI + cloud agent): `{"version": 1, "hooks": {<event>: [...]}}`, optional `disableAllHooks`. Entries: `type: "command"` with `bash` (script path, executable + shebang), `powershell`, `command` (cross-platform fallback), `cwd`, `env`, `timeoutSec` (default 30), `matcher` (regex, anchored `^(?:PATTERN)$`); also `http` and `prompt` types. Events (camelCase, PascalCase aliases accepted): sessionStart, sessionEnd, userPromptSubmitted, userPromptTransformed, preToolUse, postToolUse, postToolUseFailure, permissionRequest (CLI only), agentStop, subagentStart, subagentStop, preCompact, errorOccurred, notification (CLI only).
- I/O: JSON on stdin; stdout returns per-event JSON — `preToolUse`: `permissionDecision: allow|deny|ask` (+ reason, `modifiedArgs`); `postToolUse`: `modifiedResult`/`additionalContext`; **`agentStop`: `{"decision": "block"|"allow", "reason": ...}` — block forces another turn**. Failure modes: `preToolUse` command hooks fail **closed** on crash/non-zero exit; exit 2 = deny for `preToolUse`/`permissionRequest`, warning elsewhere; **timeouts always fail open**.
- VS Code (Preview) reads the same `.github/hooks/*.json` location plus Claude Code's `.claude/settings.json`[`.local`] / `~/.claude/settings.json`, with 8 PascalCase events and **matchers parsed but ignored** (hooks fire on every tool call); tool input is camelCase vs Claude Code's snake_case. One `.github/hooks` file can serve CLI + cloud agent + VS Code, with event-name casing the compatibility risk.

### Custom agents, plugins, MCP (VS Code)

- Custom agents: `*.agent.md` in `.github/agents/` / `.claude/agents/` (repo), `~/.copilot/agents/` (user); `description` required, 30,000-char body cap; supported on VS Code, CLI, github.com (+ JetBrains/Eclipse/Xcode in preview). Not needed by the vault — skills are the portable unit.
- Plugins: Agent Plugins 1.0 (`plugin.json`), Claude plugin format auto-detected; marketplaces are git repos; CLI plugins auto-discovered from `~/.copilot/installed-plugins/`.
- VS Code MCP: `.vscode/mcp.json` (workspace), user-profile `mcp.json`, `${input:...}` for secrets, optional sandbox mode.

## Wiring implications (what the adapter should do)

- Ship a **real** `.github/copilot-instructions.md` (thin bootstrap pointer) — it is the only channel reaching github.com Chat, Eclipse, and Visual Studio, and it costs nothing elsewhere (instructions combine; dot-paths are outside the vault's validated corpus).
- Ship a **real** `.github/hooks/` agent hook: `agentStop` → run `brain validate`, return `decision: block` with the error output when validation fails **in the cloud agent only** (locally a half-edited note is normal state and pre-commit is the gate). This closes the cloud-agent enforcement gap (git pre-commit likely bypassed, CI gated behind human approval). Needs a repeat-block guard — `block` forces another turn and nothing in the schema stops a loop until the 59-minute cap. Fail-open on timeout is acceptable — CI remains the backstop.
- Do **not** ship `copilot-setup-steps.yml` (nothing to install — stdlib-only was the point), `.github/instructions/` files (AGENTS.md already reaches every agent surface that path-specific files reach), prompt files (legacy), or custom agents (skills are the unit).
- Fix onboard-harness's Copilot story: register the vault's real `10_Agents/skills/` directory (`copilot skill add`, reversible via `copilot skill remove`) or **copy** skill folders into `~/.copilot/skills/` instead of relying on `~/.agents/skills/` symlinks (`chat.agentSkillsLocations` is documented for *project* locations — user-scope use unverified); user-scope memory pointer goes in `~/.copilot/copilot-instructions.md` as **plain text** (absolute/`~/` `@`-references are not loaded).
- Document the CI approval gate, Agents secrets, the firewall, and `--allow-tool` semantics in the wiring doc.

## Still unverified (consolidated)

- Whether repo-configured git hooks (`core.hooksPath`) fire on cloud-agent commits — no doc addresses it; treat as **no** and rely on agent hooks + CI.
- Whether `shell(cmd)` allow-filters match invocations with appended arguments; compound-command (`&&`, pipes) handling.
- Extra top-level SKILL.md frontmatter keys: officially undefined (works in practice; spec's `metadata` map is the sanctioned location).
- Whether symlinked skill dirs work after #1021's close; whether `~/.agents/skills` is reliably discovered by the CLI.
- Whether VS Code accepts camelCase event names in `.github/hooks/*.json` (its docs show PascalCase; GitHub's docs say PascalCase aliases are accepted on their side).
- AGENTS.md-vs-CLAUDE.md tiebreak when both exist (docs define none; instructions combine); VS Code defaults for `chat.useAgentsMdFile`/`chat.useClaudeMdFile`.
- JetBrains path-specific support (GitHub's two pages contradict each other).
- Whether untrusted CLI directories skip instructions/skills/hook loading (trust is documented as a file-access gate only).
- Where `copilot skill add` persists its registration (no documented storage location; removal is via `copilot skill remove` / `/skills remove`).
- When `agentStop` fires in an interactive CLI session (every turn end vs session end — inferred from the event name only).
- Whether `disableAllHooks` in a user-scope hooks file disables repo-shipped hooks, or only entries in its own file.
- Whether `chat.agentSkillsLocations` set in VS Code *user* settings loads out-of-workspace absolute paths in every session (documented for project skill locations).
